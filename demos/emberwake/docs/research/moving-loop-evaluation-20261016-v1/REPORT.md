# Small moving-loop evaluation protocol

The next useful evidence is unchanged normal-speed playback plus fixed-camera travel at the actual game speed. Onion skins and decoded stills can diagnose a reported issue, but cannot establish human motion or controller acceptance. This research does not revise the frozen art review or assign an art score.

Research date: **2026-10-16**. Preferred six-month window: **2026-04-16 through 2026-10-16**. Four primary sources were selected: one recent practitioner guide and three official, older-standing/undated documentation pages. Documentation crawl dates are not publication dates.

| Source and date | Evidence and its limit |
|---|---|
| [Harvey Newman / Animworks, Walk Cycles](https://anim.works/walk-cycle/), **2026-08-24**; within window | Author-written animation guidance distinguishes contact, weight-taking/down, passing/swing and push-off; recommends checking planted feet against ground, then translating an in-place cycle at stride speed. Its neutral 24-fps/one-second example is explicitly a baseline rather than a rule. It is Maya-oriented practitioner advice, not a controlled study or a required duration for this stylized sprite. |
| [Godot 4.5 SpriteFrames](https://docs.godotengine.org/en/4.5/classes/class_spriteframes.html#class-spriteframes-method-get-frame-duration), **publication/update date not stated**; older versioned documentation | Documented API behavior: frame duration is relative; absolute seconds = relative duration / (animation FPS × absolute playing speed). Doubling relative duration doubles exposure. Use the pinned 4.5 page as an explicit version reference, not a claim about the local project's version. |
| [Aseprite Onion Skinning](https://www.aseprite.org/docs/onion-skinning/), **publication/update date not stated**; older-standing documentation | Documented editor behavior: F3 enables onion skin; previous/next-frame counts and red/blue tint are configurable. This documents a comparison tool, not an automatic anatomy, contact or quality validator. |
| [Godot 4.5 Fixing jitter, stutter and input lag](https://docs.godotengine.org/en/4.5/tutorials/rendering/jitter_stutter.html), **publication/update date not stated**; older versioned documentation | Official guidance distinguishes jitter, intermittent stutter and input delay, and notes time-source/refresh mismatch. It requests reproduction information and captures for reports. Transform interpolation addresses a rendering/movement timing problem; it does not add or repair sprite drawings. No runtime setting change is proposed here. |

The following protocol is **design advice inferred from those sources**, with direct calculations called out. It has not been executed in this research task.

1. **Bind the unchanged experiment.** Record bank/direction, ordered PNG SHA-256 values, pivot, scale/filter, all holds, loop boundary, runtime version, game movement speed, render/capture FPS and display refresh. Keep art and timing fixed for the first test. Do not add an extra copy of pose 00 at the loop end. Any later art or timing change creates a new test identity.
2. **Check intended timing before judging it.** For the supplied eight equal 9/160-second holds, each hold is 56.25 ms, loop duration is 0.45 s, and frame onsets are 0, .05625, .1125, .16875, .225, .28125, .3375 and .39375 s. Godot's documented formula would represent equal relative durations of 1 at FPS = 160/9 and playing speed 1; verify the actual project rather than assuming it uses that setup. Log frame-change times and inspect encoded capture PTS separately. A 60-Hz display has **3.375 refresh intervals per hold**, so equal authored holds need not occupy equal numbers of captured display frames. These numbers are arithmetic, not observed playback evidence.
3. **Make four short takes, not another large art batch.** For each bank × NE/NW direction, record one take containing 4.5 s of an in-place preview and 4.5 s of constant-speed gameplay travel with the camera fixed to the world. Each half covers ten declared loops. Use the current game movement speed and a marked ground/tile grid; keep real terrain and the actual game-scale/nearest presentation visible. The stationary preview isolates the drawing cycle; fixed-camera translation exposes its relationship to world travel. Do not infer foot sliding from the in-place preview alone. Record the transition between the two test modes as setup, not a gait defect.
4. **Have a human view normal speed first.** Randomize anonymous A/B order and view at game scale before enlargement or slow motion. Record only: cadence readable; alternating legs understandable; loop seam distracting; visible support foot drifts relative to ground; identity/material pops. Use yes/no/uncertain with a time and frame/pair for each concern; no new overall art score is needed. Then use quarter-speed playback and frame stepping to locate the same concern. Slower playback is diagnostic and does not substitute for the first normal-speed response.
5. **Diagnose only the reported pair.** With one previous and one next onion skin, follow the same visible boot, pelvis and hem across the reported pair and wrap when relevant. Distinguish a held drawing from changed exposure, uneven pose spacing from render stutter, and a hidden joint from a detached one. Do not require equal screen-space movement or an open gap in every pose: perspective, leg overlap and support/swing differ. Record an occluded boot/contact as uncertain rather than inventing a contact point. This interpretation is an evaluation heuristic, not a guarantee supplied by Aseprite.
6. **Choose one small experiment after classification.** If timing logs/capture cadence disagree with the ledger, resolve that evidence issue first. If human playback isolates a support/swing spacing problem, test either one hold adjustment **or** one local drawing change, keeping the other variables fixed. If only stylistic cadence preference remains, record it as preference. Repeat only the affected bank/direction, plus its wrap and relevant start/stop transition. Do not run a broad regeneration pass on the basis of an uncertain still-image hypothesis.

A visible support-foot check can be made explicit: under a fixed camera, track a human-identified sole/contact point in world space during its supposed support interval. Its world position should remain approximately near the same marked ground location for a non-sliding walk; the swinging foot should advance to the next placement. For a simple untranslated screen plane, world displacement is root displacement plus local-point displacement. In top-down projection, track against the rendered ground plane and retain uncertainty about hidden vertical motion. This is an inferred diagnostic, not a claim that every pixel of a stylized boot must stay fixed or that a 2D sprite reveals physical contact.

Minimum output is four short takes, one timing/environment ledger and a short issue table: bank/direction, normal-speed observation, time/pair, visible point or occlusion, timing/render/art/preference classification, smallest next experiment, and human reviewer. No art edit is needed to collect this evidence. Human controller acceptance, if wanted, must be recorded during actual interactive play, separately from video review.

A still-image model can verify hashes, hold arithmetic, timing logs/PTS and frame order; inspect source pixels, alpha, onion skins and sampled positions; and propose bounded hypotheses. **It must not report that it personally experienced smooth normal-speed motion, weight, foot planting or controller feel from contact sheets.** A timestamp-correct file also does not prove it was displayed correctly on the reviewer's hardware. Distinguish intended timing, encoded timing, observed runtime/capture timing and human perception in the result.

No AI generation source was selected because a new generation method is unnecessary for evaluating unchanged loops. No model, provider, paid service, installation or generation is proposed. No inference about PixelLab internals is made. The previously covered arXiv/SPA/PixelLab material was not used as evidence for this report.
