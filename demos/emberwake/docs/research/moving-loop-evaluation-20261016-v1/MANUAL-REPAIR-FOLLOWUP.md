# Source-led repair follow-up

Read on 2026-10-16. These are public workflow descriptions, not evidence of a private model architecture. The documentation pages have no verified publication date; crawl dates are not publication dates.

The [PixelLab skeleton workflow](https://www.pixellab.ai/docs/tools/animate-with-skeleton) describes manual checks of every skeleton, frozen reference frames, init images and bounded inpainting. Its recommended loop includes rough manual corrections followed by regeneration with increasing init strength. Its fixed-head option constrains a reference skeleton; it is not proof that arbitrary generated RGBA head pixels remain exact. The page describes an editor workflow, not an assertion that the current REST API exposes identical controls.

The [Aseprite animation documentation](https://www.aseprite.org/docs/animation) describes an editable frame/layer/cel timeline, explicit frame durations and preview playback. [Onion skinning](https://www.aseprite.org/docs/onion-skinning/) supplies adjacent-frame drawing context. These tools help locate and repair a cuff or hip join; neither an onion overlay nor a correct timeline verifies believable movement.

Applied here: keep failed contact constructions frozen; repair a small, declared pelvis/cloth owner rather than hiding a gap with an undeclared pasted strip; preserve complete painted boots when their surface should remain rigid; use whole-cel ImageGen banks as a separate comparison to four-key part interpolation. Each changed result gets a new frozen full-cycle packet at the same duration and intended scale. Manual repairs retain source addresses, authored-paint masks and actual undo/replay history. Browser timing checks, ordered-still criticism, human continuous playback and actual Godot acceptance remain separate.

No new package or model was installed for this follow-up. No PixelLab generation, H3 call, local generative model or private-service inspection occurred.
