The scenario waits for attack time >= .30 or cast time >= .39, then reads current state in a separate browser command. A later diagnostic assignment can replace the matching snapshot before that second read. Opposite-key delivery also follows an initial wait and read. Historical JSON contains successful point samples, not the intermediate emissions or input-delivery timestamps: it cannot establish a missing emission, delayed input/wait, the wait/read race, or a gameplay defect as the timeout cause.

Important correction: comparing a 110 ms late window with a nominal seven-tick/116.7 ms diagnostic cadence alone does **not** prove omission. At a steady 60 Hz, eligible attack ticks 18 through 24 cover all seven phases. An eight-tick gap can miss the entire late window (action ticks 1, 9, 17, 25). A binary accumulation just below .30 is another possible boundary issue, not demonstrated for this run. The proposal preserves the exact original threshold, with no added epsilon.

The exact candidate and unified patch are in `proposed/` and `proposed.patch`. They touch only these three files:

- `scripts/browser_diagnostics.gd`: use `SNAPSHOT_INTERVAL := 1.0 / 30.0`; keep `elapsed += delta`; replace the .1 gate with that constant; replace zero reset with `fmod(elapsed, SNAPSHOT_INTERVAL)`. At steady 60 Hz, publication is every two frames, about 33.3 ms, providing several samples in the existing late window. Fractional carry avoids systematic loss; one current snapshot after a render stall avoids a burst of duplicate observations. This changes observation cadence only. It triples nominal diagnostic JSON/bridge work; actual browser overhead remains unmeasured here. Render stalls can still create gaps, so lack of required evidence remains failure.
- `tests/browser_eight_directions.js`: return the matched state object from `waitHero`'s JSHandle directly; use that return at idle call sites. Install a recorder **before** the real action key, issue real opposite keys immediately afterward, and observe distinct existing snapshots in a bounded RAF trace (2.5 seconds, 96 snapshots, no replay or retry). Capture physics tick, rendered-frame count, observer time, FPS, hero fields, and projectiles. Stop on observed action completion; retain every trace and action/error phase in the report. Cancel/delete only the recorder's own temporary window property. Real input is still the sole game control.
- `tests/run_browser_eight_directions.py`: defensively fail if any receipt is incomplete or failed, even if a scenario incorrectly returns `passed:true`.

Acceptance checks every observed locked snapshot for committed facing/vector, and every observed released locked snapshot for empty pending hit. It requires actual opposite movement input during release/recovery, and at least one such sample at the **original** late threshold while `state_left > 0`. Filtering must never remove bad facing/vector/pending-hit samples before assertions. Missing start, completion, released opposite input, original-threshold late sample, or current-cast projectile is explicit incomplete/fail. Cast direction checks use all observed current-cast friendly projectile samples, with inferred birth tick excluding earlier bolts; diagnostics lack projectile IDs, so this remains a sampled direction check, not exact launch proof.

The attack screenshot request starts after opposite input while the action is running; it is not a release-frame proof. Native frozen screenshots retain that separate role. The trace also does not prove unobserved physics ticks were correct. Native passes do not replace this browser gate.
